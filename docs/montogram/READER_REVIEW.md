# Reader batch: distinct actions and limits

M47 opens one selected ordinary message as an accessible plain-text reader, bounded to32768 UTF-16 units and a720dp column. M48 searches only this transient reader (query128 units,256 hits plus truncation marker, Unicode code-point boundaries, simple Java case matching; no normalization/full case-fold). M45 is explicit temporary plain-text copying, with one opaque per-copy UUID ownership token and one60-second main-loop callback. These are separate actions, not a count of button variants.

Reader is opt-in (`reader=false` by default). Native menus and copy behavior remain unchanged when disabled. Capture and callbacks require current account/self/peer, the same cached message object and text, known peer forwarding flags, and the strict bookmark eligibility predicate: no secret, TTL/ephemeral, protected, paid, grouped, spoiled, sponsored, deleted or scheduled content. The captured plain message text never enters fragment args, saved state, files, logs or a network request. Text/query/views and authorization references are cleared on pause, focus loss, logout/account switch and account deletion/replacement/peer-info notifications. Notifications conservatively close even for unrelated changes in that account, so the reader does not depend on parent-cache notification order. Rendering and actions revalidate the lease. The parent ChatActivity can be paused while Reader is visible; it is held weakly.

Temporary-copy creation needs foreground/current-account authorization. Cleanup of an already-owned clip intentionally does not depend on foreground/account: it makes one best-effort attempt, catches Android access denial, and forgets app-owned references. Before reading payload or clearing, it requires the exact random label, one plain-text MIME, one item with no URI/Intent/HTML, and the exact original text. Replaced clips are left alone. A failed replacement copy preserves the previous pending cleanup; only successful installation cancels it. API28+ uses clearPrimaryClip, earlier versions replace the owned clip with empty text. There is no Android atomic compare-and-clear API; OS permission races, process death and keyboard/clipboard history mean erasure cannot be guaranteed. UI discloses this. No clipboard listener, service or extra worker thread is added.
